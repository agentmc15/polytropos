Guardrails, safety and hardening in polytropos

polytropos dispatches coding agents, runs the checks a kit names, and writes execution state. Running a kit's checks is intentional code execution, so its safety comes from naming exactly what is confined, what is gated, what is only recorded, and what is not a boundary at all. This page lists every guardrail, how each one is built, the test that proves it, and the stages where it acts. SECURITY.md is the policy; this page maps it.

Part 1

The posture

Three ideas hold the rest together: the approval line follows reversibility, the tool is for repositories you control, and only one thing runs inside an OS boundary.

Where the approval line sits

The line between what runs unasked and what waits for you is reversibility, not task size. Each lane is a code path, not a policy a model is asked to follow.

Reversible work

Runs without asking

Reading, planning, checking and rehearsing. Every demo, --demo and --dry-run path is synthetic or spawns nothing; harness_update.py check and preflight, exec_policy.py check and the docs generators' check compare and write nothing.

Consequential actions

Prepared, then gated on one named switch

Spending needs --live with --max-usd. Writing a harness home goes only through harness_select.py install or harness_update.py apply, and overwriting what it does not own takes --adopt-existing. Leaving the OS boundary is --exec-mode trusted-host; restoring a reviewer's blanket grant is --review-permissions bypass. Each opt-out reports itself.

Irreversible actions

Never on the engine's own initiative

Nothing relocates a store. The one deletion, runtime_data.py forget, is a dry run unless given --apply. Installation never overwrites what it does not own, and harness_update.py apply prints the ~/.claude remedy rather than running it.

Who it is for

polytropos is appropriate for repositories you control, run by the person who owns the machine. It is not an isolation boundary for unattended execution against untrusted repositories from a credential-rich host.

An outer sandbox — a container, a VM, a separate user account — is what limits host exposure today. polytropos does not provide one, and a kit is trusted input: its verify commands are code.

The execution boundary

During a headless kit run, only the verify command runs inside the OS boundary. The model dispatch runs with your privileges, because the sandbox blocks the Keychain where subscription credentials live.

Part 4

What is not a boundary

Do not rely on any of these. Each is a known gap, stated so that the controls above are not read as stronger than they are.

Model dispatch is not confined

The macOS sandbox blocks the Keychain, where subscription credentials live, so a confined model CLI cannot log in. A dispatch runs with your privileges, your network and its provider's login.

The interactive loop's own checks are not sandboxed

exec_policy confines a check when a driver, the verify hook's precheck or drift runs it. In the interactive /polytropos:execute loop, the orchestrator runs each verify command through the session's own shell.

Linux and Windows have no sandbox backend

--exec-mode enforced refuses there, and only the explicit trusted-host mode runs. That is a stated gap, not a silent downgrade.

A worktree or a scheduler copy is not a sandbox

Separate directories separate files and writes. They do not separate privileges, credentials or network access, and a worker reading a file another is changing is not detected.

Benchmark candidates and judges are not yet confined

A protected-experiment profile exists in bin/exec_policy.py, but nothing dispatches through it yet; benchmark setup and test commands run with the driver's privileges.

Role names are not permissions

A prompt that says read-only does not make a reviewer read-only. A tool pin that includes Bash reaches everything a shell reaches, Copilot has no per-tool flag, and only Codex pins review to a read-only sandbox.

Execution state is not tamper-proof

TASKS.md, NOTES.md and the verify markers sit in the tree a worker edits. Edits are detected and reported, not prevented, and the ledger outside the tree is out of a confined check's reach but not an unconfined dispatch's.

A spend cap is not a provider cap

Budget dials and --max-usd stop polytropos from dispatching. They cannot stop a provider from billing, or undo spend already incurred.

A capability nobody has run is not a control

Most capability rows say unknown, and that is the honest state until someone runs them.

Redaction is shape-matching

It catches strings shaped like published credential formats. A password that reads as a word, a name or an address has no shape and is not caught.

Recording an attempt is not exactly-once execution

A process killed at its limit may already have been billed or written a file. The ledger closes it as unknown and never replays it; it cannot know what the provider billed.

An isolated summary is not proof the model had no tools

The journal summary is shown to have run outside the project and written nothing there. No tool-restricting flag is passed.

drift cannot yet tell a nested sandbox from real drift

A check that starts its own sandbox is refused inside drift's, and reads as drifted.

Kits are trusted input

A kit's verify commands are code. Running a kit you did not write is running its scripts.

Repository settings are not set by code

Dependabot, secret scanning and push protection are account switches; nothing here claims they are on.
