Spec-driven development: a guide, with polytropos

A guide to spec-driven development, a map from the practice to polytropos and from polytropos back to the practice, and an assessment of what polytropos should build next.

How to read this guide. Part 1 is about spec-driven development itself and names no polytropos feature. Part 3 goes the other way: every polytropos component and the idea it implements, including the ones the practice has no name for. Part 4 assesses where polytropos stands and what it should build next.

Companions: docs/sdd/core-four.md maps Spec Kit's phases one by one; docs/SPEC-DRIVEN.md is the long form of how polytropos works; docs/spec-driven-pitch.html is the four-page pitch. Part 1 · Spec-driven development

What it is

Spec-driven development (SDD) means writing down what a change must do, and how it will be checked, before an AI agent writes the code, and then holding the agent's work to that written spec rather than to the conversation that produced it.

The problem it answers is specific to agents. An agent given a prompt builds what it understood, and reports success in the same confident voice whether it succeeded or not. Without a written spec there is nothing outside the conversation to check the result against, so review falls back on reading the code and trusting the summary. Iterating on prompts until the output looks right is usually called "vibe coding". IBM's primer names three debts it builds up: context drift, where a fix in one place breaks another; fragmentation, where new code ignores the existing architecture; and token cost, from long prompting cycles that fix what a clear spec would have prevented.

The idea is old. SDD descends from test-driven development, which writes the test before the code, and behavior-driven development, which writes the behavior before the test. SDD moves one step earlier still and asks whether the change has been defined at all. What is new is the executor: a model that can produce a lot of plausible code quickly makes the spec the one fixed point that every step is checked against.

The field has not settled what belongs in a spec. Spec Kit keeps technology choices out of its specify step and puts them in a later plan. IBM's definition includes implementation details, agreed before coding starts. Most practitioners split the difference: the what and why first, reviewed on their own, then the how.

The levels

Birgitta Böckeler's analysis on martinfowler.com sorts SDD by how long the spec lives and who edits it. IBM's primer adds a fourth, hybrid level.

LevelWhat happens to the specExample
Spec-firstWritten for a change, used to build it, then set aside.Kiro; most tools in practice
HybridKept as a versioned record of the change, like an architecture decision record, but not maintained.Specs as ADRs; issue trackers as the source of truth
Spec-anchoredKept and maintained for the feature's lifetime. Automated tests, often in CI, tie the spec to the code and catch drift.OpenSpec; Spec Kit's stated aim
Spec-as-sourceThe only thing people edit; code is regenerated from it.Tessl (reported as in beta); Spec Kit's long-term vision

Böckeler's finding, as several summaries report it, is that most tools claim a higher level than they deliver. Spec-as-source has "the least field evidence behind it", in Panaversity's words, and regeneration is non-deterministic. Spec-anchored is widely called the defensible middle, and the usual advice is to start spec-first and grow into it.

Panaversity's crash course gives the reason for the early gates: clarification is "the cheapest place in the entire process to fix a mistake". Its rule for a gap found mid-build is to fix the spec first, so that the spec's history and the code's history tell the same story.

Principles

These recur across the tools, Böckeler's analysis, Anthropic's harness research and the practitioner literature. The first ten are common ground. The last two are rarely stated outright, and they are where agent-era SDD most differs from its ancestors.

  • P1 · Intent before implementation. Write the what and why before any design or code.
  • P2 · A person approves the spec. Requirements are signed off before design starts.
  • P3 · Standing rules, enforced. Project-wide constraints apply to every change. Panaversity warns that a rules file is "persistent context, not enforced law", so the rules that must never break need tests, hooks or CI behind them.
  • P4 · Testable acceptance. Every requirement can be checked, ideally by a command.
  • P5 · Design with reasons. Decisions are recorded with their rationale.
  • P6 · Small, ordered, traceable tasks. Tasks have ids and dependencies, and trace to the plan.
  • P7 · Verified independently. The work is checked against the spec by something other than the agent that built it. Anthropic found that agents "reliably skew positive when grading their own work".
  • P8 · Spec and code stay in sync. Drift is detected, not discovered.
  • P9 · Changes are specified as changes. For existing code, the spec says what is added, modified and removed.
  • P10 · Right-sized ceremony. In IBM's words, "the cost of refining the spec should always be lower than the cost of fixing misunderstandings in implementation." A one-line fix needs no plan.
  • P11 · Spend judgment where it pays. "Plan with a strong model, implement with a cheaper one," as Panaversity puts it: the expensive reasoning goes into the spec, and execution runs cheaper.
  • P12 · Measure the spec, not just the code. Record when a spec itself was wrong, so the next spec is better.

Writing a good spec

A spec is good when a stranger could build the right thing from it, and could not build the wrong thing while still satisfying it. In practice:

  • One goal and a checkable "done". "Checkable, not vibes": a person or a command can say whether it holds.
  • An explicit out-of-scope fence. What the change must not touch. Executors and reviewers enforce this later, so it does more work than it looks.
  • Acceptance criteria that can fail. A check that would pass before the work proves nothing. Spec Kit's constitution makes the same point for tests: they are "written, approved, and confirmed failing before implementation".
  • Edge cases and inputs named. Inputs, outputs, data shapes, error paths.
  • Decisions with their reasons. The reason is what lets the builder make the next hundred small decisions consistently.
  • Contracts pinned, implementation open. Exact interfaces and file paths; freedom in how the code is written. Anthropic's planner stayed high-level for the same reason, because otherwise "the errors in the spec would cascade into the downstream implementation".
  • Self-contained tasks. Each task should be buildable by someone who has not seen the conversation. Panaversity calls this the stranger test.

Two line-by-line tests catch most bad specs. The wrong-build test: could "a competent person build the wrong thing and still technically satisfy this line"? The red-first test: would this acceptance check have failed before the work began?

When not to use it

SDD fits work whose outcome can be stated before it starts. It fits exploration poorly, where the point is to find out what to build, and it costs more than it returns on changes small enough to check by reading the diff. Anthropic's version of the cost rule is about review rather than specs, but it generalizes: an evaluator "is worth the cost when the task sits beyond what the current model does reliably solo."

Practitioner comparisons place the tools on a ceremony scale, with OpenSpec lightest, Spec Kit in the middle and BMAD heaviest, and report time and cost rising with ceremony. Those are single-author trials with their own rubrics, not controlled benchmarks.

Anthropic's harness research deserves a closer look than its place in the table suggests. In "Harness design for long-running application development" (March 2026), Prithvi Rajasekaran of Anthropic Labs ran a three-agent design on multi-hour builds. A planner expands a short prompt into a product spec, a generator builds it one feature per sprint, and an evaluator tests the running app like a user, with a hard threshold per criterion: "if any one fell below it, the sprint failed." Before each sprint, generator and evaluator agree "what 'done' looked like". Agents hand work to each other through files, and a context reset starts "a fresh agent" with "a structured handoff".

Its findings are the field's best evidence on verification. Self-grading is lenient. A separate evaluator, out of the box, would find real issues and then "talk itself into deciding they weren't a big deal and approve the work anyway", until the author tuned it by reading its logs for "examples where its judgment diverged from mine". And the parts of a harness should change as models do: "every component in a harness encodes an assumption about what the model can't do on its own." The full harness cost over twenty times as much as a solo run, which buys quality with spend. The evidence comes from a small number of runs.

Part 2 · From spec-driven development to polytropos

polytropos is a Claude Code plugin. /polytropos:architect writes the spec once on the frontier tier, as an execution kit in .claude/kits/<slug>/. /polytropos:execute builds against it task by task on cheaper tiers, and checks every task against the kit rather than against the builder's report. A ledger in the kit's NOTES.md records how it went. This part maps the practice onto that system.

Spec Kit, phase by phase

Spec Kit is the closest tool, mapped in full in docs/sdd/core-four.md. Its constitution splits into CLAUDE.md and GUARDRAILS.md. Specify and clarify become the spec half of PLAN.md with the approval pause. Plan becomes the design half. Tasks becomes TASKS.md, where Spec Kit's parallel marker is an explicit independent: yes. Implement becomes the execute loop, and converge corresponds to the loop ending only when every task is done. Spec Kit's Article III states test-first as a principle; polytropos's red-green rule enforces it at run time. Spec Kit's plan template checks the design against the constitution in a "Phase -1" gate, which polytropos has no counterpart for.

The sharpest difference is cost. Their harness buys quality with spend and describes no split of models between its agents. polytropos claims the reverse trade, and its ledger is how that claim gets tested: when the verifier tier is wrong, the record shows it, which is how polytropos moved its default verifier from haiku to sonnet.

The other tools

  • Kiro. Its requirements.md, design.md and tasks.md correspond to the two halves of PLAN.md and to TASKS.md, and its steering files to CLAUDE.md and GUARDRAILS.md. Kiro gates after each phase; polytropos gates once, after the spec. Kiro's hooks fire on file events; polytropos checks at fixed points in its loop instead. EARS notation has no counterpart.
  • OpenSpec. It keeps a living spec and writes each change as a delta. polytropos writes a fresh spec per change and keeps the finished kit as a record, not as a living spec.
  • BMAD. Its persona pipeline corresponds to polytropos's roles: the standing implementer, verifier and reviewer, plus seven optional ones declared on a roles: line. The difference is that polytropos roles are opt-in and measured: the routing guidance keeps a role only "when its measured marginal value earns its measured cost".
  • Tessl. It aims at regenerating code from specs; polytropos is "not code generation from a formal spec". It offers verification instead of determinism: a rerun may write different code, and the same checks judge it.

What polytropos adds that SDD has no name for

  • A price on every task. The spec says which model builds each part. That makes cost a design decision, written next to the acceptance criteria.
  • Escalation with evidence. A failed task reaches the frontier tier carrying only its brief, its failure output and the relevant plan excerpts, so frontier spend tracks difficulty.
  • A graded spec. Executors are graded in every agent system. polytropos also grades the planner, by kind of brief defect, across every kit.
  • Measured review. Each review role's findings, confirmed findings and catches that no earlier check made are recorded, so whether a role is worth its cost is a question with an answer.
  • Bounded autonomy. Re-routing moves only upward, one tier at a time, never to the frontier, and budget caps stop a run and say so instead of ending it quietly.

Part 4 · Assessment and roadmap

Where polytropos stands

On the levels of Part 1, polytropos is hybrid: each kit is a spec for one change, committed and kept as a record but not maintained afterward. Within a run it behaves like spec-anchored, because every task is checked against the spec and stale evidence is detected. It is strongest where the field is weakest, in independent verification (P7), spending judgment where it pays (P11) and measuring the spec (P12). It is weakest at keeping specs in sync after a change ships (P8), at checking artifacts against each other before a run, and at right-sizing (P10).

What its own ledger says

The ledger is the best evidence for what to improve, because it records where specs actually failed. python3 bin/routing_scorecard.py --history lists every brief defect by kind across every kit. When this guide was written, on 2026-10-24, the most frequent kinds were contradictory acceptance, stale plan decisions, stale pins (references to files or lines that had moved) and unspecified paths. Most were caught mid-run, after dispatches had already been spent. The same card showed several kinds outside the sanctioned vocabulary, coined mid-run, which splits recurring problems across synonyms. python3 bin/routing_scorecard.py --roles showed red-team and test-author with the highest rate of catches no earlier check made, on small samples. Re-run both commands before acting on any of this.

The interactive execute loop does not record the file versions that kit_contract.py freshness compares, so freshness reports every task of an interactively run kit as unknown. The headless drivers record them.
