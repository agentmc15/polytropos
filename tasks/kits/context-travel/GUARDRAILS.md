# Context travel guardrails

- CT1–CT5 are complete within their offline scopes, including thin skill
  integration and offline packaging across all six requested surfaces.
  CT6 is not dispatched. Fixture-only packaging writes use temporary homes.
  No graph extraction, persistent cache, HTTP server, skill installation,
  provider adapter, dispatch, repair, merge, or deployment.
- Do not change existing kit/task readiness, status, pricing, or acceptance rules.
- No real codex, copilot, claude, Cursor agent, graphify, paid provider, or external
  network calls in verification. Synthetic numeric-loopback fixtures are allowed.
  Use stdlib unittest, temporary fixtures and stubs only.
- No personal homes, credential stores, or unrelated transcripts. No inferred
  repository identity and no migration or fabrication of old ledger records.
- Apply the global anonymous commit conventions. No publication or GitHub changes.
- Use canonical encoding for identity, not concatenation with ambiguous delimiters.
  A digest is not authentication and a briefing grants no authority.
- Reader inputs select roots and files explicitly. No directory enumeration,
  fallback search, implicit store, home lookup, Git probe, clock or environment
  discovery. A selected file being stable during its read does not prove current
  graph provenance or a transactionally consistent multi-file snapshot.
- Enforce denials before opening selected content, including graph/source/evidence
  paths. All physical bytes read count toward limits, including failed attempts.
  Preserve mandatory task/criteria data or refuse the source; do not silently trim.
- Reuse pure kit/graph/ledger parsing. Existing file-loading entry points must not
  run before the new boundary. Source observations are advisory data, never new
  authority or migrated history. Preserve existing callers' default behavior.
- CT1 source, tests and schema remain unchanged unless a concrete defect is first
  reported. The coordinator owns release registration and generated documentation.
- CT3 is pure projection over explicit in-memory inputs. No reader invocation,
  file/store access, repository probing, clock, environment or process calls.
  CT2 runtime/schema and existing authority engines remain unchanged unless a
  concrete blocking gap is reported before an edit.
- Never rehash redacted acceptance text as the original acceptance identity.
  Unbound history remains unbound; source consistency does not prove freshness.
  A recorded pass/status is not acceptance, independent verification or readiness.
- The lifecycle view's complete/partial/refused status describes the projection,
  never work acceptance. Critical limitations travel with each role brief; an
  insufficient budget refuses rather than trimming criteria or critical caveats.
- Keep implementation in the isolated public candidate, then synchronize the
  identical tracked content to the isolated private CT1 candidate. Leave the
  original public checkout and separate critique checkout untouched.
  The coordinator owns task state,
  evidence notes, release integration, and final acceptance.
- Startup bindings authorize explicit roots, kits, selected source files, deny
  rules and limits. Tool arguments cannot expand those grants. Imported artifacts
  also require an authorized repository/kit subject before projection or compare.
- Use the existing confined stable reader for the explicitly selected startup
  config. No cwd/home/store lookup, path expansion, extra source probing or
  implicit MCP roots. Do not echo config, absolute paths or bad inputs in errors.
- Bound JSON bytes, depth, collections, frames, response size and session state.
  Preserve mandatory criteria/critical limitations in JSON and text, or refuse.
  Synchronous calls cannot promise active cancellation or live client support.
- CT1–CT4 runtime/schema/tests remain frozen absent a reported concrete blocker.
- CT5 uses the existing query, source, identity, lifecycle, installer and pricing
  authorities. No new dispatcher, source scan, MCP registration or client config.
  Keep context on demand and advisory; absence/refusal never bypasses verification.
- Six surface records keep seven modes, including separate Claude Desktop chat
  and Code modes. Product documentation, package implementation and installed-client
  verification remain separate; offline fixtures cannot promote the latter.
- Public source parity is required. After CT5, the coordinator prepares reviewed
  local synchronization; no publication, active public-checkout overwrite or
  copying personal/generated runtime data. Private GitHub capability differences
  must not create a separate product implementation.
